## How to read the graph

**A box is one question**: one decision the owner holds, or one already ruled and kept as an anchor. The box LEADS with the question it is asking, in the declaration's own words; under it sits the identifier this index is keyed by with its matrix row in brackets, and then one line per alternative it offers. Listing an alternative selects nothing.

**The fill colour is the status, and nothing else.**

- A **pale yellow** box (#fef3c7) is `Open`: nobody has decided this and no recommendation is recorded. There may still be alternatives listed; none of them is being put forward.
- A **pale green** box (#dcfce7) is `Lean`: a recommendation is recorded with the evidence it rests on, and you have not ratified it. The starred alternative in the box is that lean, and a lean selects nothing.
- A **pale blue** box (#dbeafe) is `Directed`: you gave direction and it is recorded. Ratification, publication or a witness is still pending, so the question is not closed.
- A **pale grey** box (#e2e8f0) is `Decided`: ruled. It is kept in the graph as an anchor the open questions hang from, so a change to it is visibly a change to everything below it.
- A **near-white** box (#f8fafc) is not a status: a near-white folder is not a question at all. It is a trigger: an external need or event that must happen before the question it gates is worth answering.

**The three arrows.**

- A **solid dark blue** arrow (#1f4e79) is `Requires`: drawn from the prerequisite to the question that waits on it. The question at the head cannot be answered until every question at a tail is decided.
- A **dashed brown-orange** arrow (#b45309) is `Implies`: drawn from a question to another question that one of its alternatives would make live, and labelled with that branch. It is a consequence, not an order: the question at the head only becomes real work if that alternative is taken.
- A **dotted grey** arrow (#6b7280) is `GatedBy`: drawn from a trigger to the question it holds. Answering earlier is speculation rather than a decision.

**A star beside an alternative is the recorded lean or owner direction.** It repeats the evidence; it never means the question has been answered. In a stream that has ruled, the alternative a ruling took reads `(selected)` instead.

**"Answerable now" means all three of these at once**: the question is not already decided, every question it `Requires` is decided, no trigger gates it, and no unchosen alternative elsewhere is what would make it live. That is the capture host's own `roots()` answer; 4 of 24 questions meet it in this stream.

**The tiers** order the table below.

- `anchors`: already decided; the fixed points the rest of the graph hangs from
- `roots`: answerable now: nothing open is above them
- `second`: one open question above them
- `third`: two open questions above them
- `gated`: waiting on a need or event, whatever their prerequisites say
- `branch-induced`: live only if a particular alternative is taken somewhere else

**A thin docstring is marked, never rewritten.** Two mechanical marks are used:

- `short`: fewer than 6 words
- `names-a-subject`: neither asks a question nor gives an instruction, so it names the subject area rather than saying what is being decided

0 records carry one, and they are listed at the end. A mark says a reader cannot learn the decision from that sentence alone, not that the decision is wrong.

### discovery_fold

*tier `anchors`, no matrix row, status **Decided**, declared as `DiscoveryFold` in `glade_decisions:GladeDecisions.discovery_fold`.*

How does a node work out what exists and who is holding it?

Settled: by folding signed records, with no consensus step anywhere on the read path. The fold is the only runtime authority, so a read stays local and replayable and nothing has to agree before a question can be answered.

It offers no alternatives: a decided anchor is a fixed point.

### key_custody

*tier `roots`, matrix row Q11, status **Open**, declared as `KeyCustody` in `glade_decisions:GladeDecisions.key_custody`.*

Who holds the keys, and what happens when someone loses every device?

This covers the root key, each device, each node and the operator's own root at organisation scale. It decides how frightening first setup has to be, and no library choice below it means anything until it is answered: proof_family and transport_key_binding are both waiting on it.

**The alternatives it offers.**

- `owner_held_only`: Nothing is minted beyond the owner's own devices, so first setup stays simple and there is no extra secret to look after. Lose every device and the identity is gone.
- `recovery_keys`: Extra recovery material is minted at first setup and kept offline, on paper or in a safe. Loss becomes survivable, and that material is now itself something to protect.
- `social_recovery`: Recovery takes several trusted principals acting together, so no single loss is fatal. It is the most to build, and it puts recovery partly in other people's hands.

**Must be decided first**: nothing.

**Deciding it is what `proof_family`, `transport_key_binding` are waiting for.**

**Sources**: `WD-1`, `AZ-7`, `SEC-55-D5`.

### lifecycle_composition

*tier `roots`, matrix row Q10, status **Directed**, declared as `LifecycleComposition` in `glade_decisions:GladeDecisions.lifecycle_composition`.*

What owns a running task: who admits it, who drains it, who cleans up after it?

The node needs owned work, admission, drain, cancellation and shutdown reports that tell the truth, with a parent resource still owned while a child's cleanup is pending. You directed sdax-rs on 2026-09-12; what is left is the witness and the dependency posture, since sdax-rs is a Git dependency until it is published.

**The alternatives it offers.**

- `dag_runner`: Run the work as a task graph with dagx or dagrs. Both fit as runners, and neither gives symmetrical teardown, so reverse-order cleanup would still have to be built.
- `graceful_shutdown_crate`: Hand supervision to tokio-graceful-shutdown. It supervises subsystems and nothing more, and its signalling is untyped, so what is being shut down is not in the types.
- `sdax_rs`: Your own declarative async lifecycle library at the runtime host, beside Shaku, with sdax, sdax-tokio and sdax-testkit. Stages 0 to 3 have landed with conformance and adversarial review, and it is consumed from Git until it reaches crates.io. **(the recorded lean, starred in the box)**
- `tokio_primitives`: Compose Tokio's own pieces in-house: JoinSet waves, a cancellation token, a task tracker and a last-in-first-out teardown stack. It was the research lean and is now the fallback; no new dependency, and the ordering rules stay ours to hold.

**Must be decided first**: nothing.

**Deciding it is what `async_witness` is waiting for.**

**Sources**: `GDL-049`, `R28`, `AR-08`, `A5`.

### scope_model

*tier `roots`, matrix row I-2, status **Lean**, declared as `ScopeModel` in `glade_decisions:GladeDecisions.scope_model`.*

What stops a record reaching a node that should not see it: wiring, trust, encryption?

Three enforcement models fit the corpus and the decision is which one the first live slice relies on. The choice sets what a node with no grant can still observe, and each branch opens a different follow-up question.

**The alternatives it offers.**

- `cryptography`: Each share's payload is encrypted, so a node without the keys routes and stores ciphertext it cannot read. It is the only model that bounds an over-trusted node, and it costs key distribution and rotation and gives up node-side folds on that tier.
  - taking it would make `blind_relay_tier` live.
- `node_trust`: A node receives whatever its operator has been granted, and the serve hop enforces the per-session grants. Simplest to build and needs no new machinery; a shared topic lets a node learn that a share it holds no grant for changed, and what its heads are. **(the recorded lean, starred in the box)**
  - taking it would make `metadata_exposure` live.
- `topology`: A node may only connect on the protocol carrying a share it is authorised for, rejected at accept time by key and ALPN. An announcement then never reaches an unauthorised node, at one connection per peer per share and churn when grants change.
  - taking it would make `traffic_budget_numbers` live.

**Must be decided first**: `grants_as_data` (Decided), `iroh_transport` (Decided).

**Deciding it is what `dissemination` is waiting for.**

**Sources**: `IrohGladeMapping §5.2`, `GDL-010`, `AZ §7a`, `INV-5`.

### version_pin

*tier `roots`, matrix row Q2, status **Lean**, declared as `VersionPin` in `glade_decisions:GladeDecisions.version_pin`.*

Do we require iroh 1.2 or later, and pin each 0.x crate exactly when we add one?

The node's lockfile is not tracked, so nothing in the repository pins iroh: a fresh clone resolves the newest 1.x, and an old checkout keeps whatever it last resolved (this one kept 1.0.2 until 2026-09-21). 1.1.0 fixed a crash on a crafted address, which matters the moment addresses are read from untrusted input such as tickets or directory records. The manifest is therefore the only place a minimum can be recorded. The 1.x line promises wire compatibility; the protocol crates are 0.x and outside that promise, so each needs an exact pin of its own when it is first added.

**The alternatives it offers.**

- `bump_to_current`: Require 1.2 or later in the manifest now, so no checkout can build a release that still has the crafted-address crash, the relay CPU pin or NAT misrouting. One tracked line; the node's tests pass on 1.2.0. **(the recorded lean, starred in the box)**
- `stay_on_lock`: Leave the requirement at any 1.x until the first real route is built. Nothing to maintain today, and nothing stops a stale checkout from building a release with the address-parsing crash when untrusted addresses first arrive.

**Must be decided first**: `iroh_transport` (Decided).

**Deciding it is what `bulk_transfer`, `dissemination`, `relay_posture` are waiting for.**

**Sources**: `IrohReview §1`, `IrohReview §11`.

### proof_family

*tier `second`, matrix row Q6, status **Lean**, declared as `ProofFamily` in `glade_decisions:GladeDecisions.proof_family`.*

What does a capability look like on the wire when a caller presents one?

Permission is already settled as records and one pure check; this is the encoding the presented proof carries. A foreign family brings its runtime and its wire format with it, and the Rust, TypeScript and Python corpora all have to agree on the bytes. identity_adapters waits on the answer.

**The alternatives it offers.**

- `biscuit`: Adopt Biscuit tokens, an existing attenuable-token family with the shape Glade already wants. It brings a Datalog runtime and an encoding we do not control.
- `macaroons`: Adopt macaroons, where narrowing a grant is a chain of caveats. The model fits attenuation well, and the encoding is again one Glade does not own.
- `taut_grants`: Keep the encoding our own: a chain of signed taut grants where each link is signed by the parent principal and may only narrow scope, with one corpus proving the three languages agree. Nothing foreign enters, and outside interoperability is unbuilt. **(the recorded lean, starred in the box)**
- `ucan`: Adopt UCAN, whose delegation semantics are close to what the grant chain already does. Since version 1.0 its proofs are DAG-CBOR in UCAN's own envelope and no longer JWT, so AZ §2's case against JWT does not apply to it. What remains is an IPLD encoding with its own identifiers, which Glade does not control and the taut corpus does not cover.

**Must be decided first**: `grants_as_data` (Decided), `key_custody` (Open).

**Deciding it is what `identity_adapters` is waiting for.**

**Sources**: `SEC-55-D1`, `AZ §2`.

### transport_key_binding

*tier `second`, matrix row Q3, status **Lean**, declared as `TransportKeyBinding` in `glade_decisions:GladeDecisions.transport_key_binding`.*

How do we say that this iroh endpoint key belongs to that Glade node?

The directory names a node by a hash of its node key and iroh authenticates the endpoint key, and nothing replicated joins the two. Address lookup, gossip peer identity and every accept-time policy need that join, and it is a record kind and a fold rule rather than anything iroh provides.

**The alternatives it offers.**

- `binding_record`: A signed record under the node's own chain says which endpoint key is its transport. The two keys stay separate and rotate independently, and it is a new record kind with a fold rule to write. **(the recorded lean, starred in the box)**
- `one_key_both_roles`: Use the iroh endpoint id as the Glade node id and drop the split. Nothing new has to be replicated, and transport key and node identity can no longer rotate or be reasoned about apart.

**Must be decided first**: `iroh_transport` (Decided), `key_custody` (Open).

**Deciding it is what `dissemination`, `relay_posture` are waiting for.**

**Sources**: `IrohGladeMapping §5.2`, `GladeDirectoryNotes ambiguity 2`.

### dissemination

*tier `third`, matrix row Q4, status **Lean**, declared as `Dissemination` in `glade_decisions:GladeDecisions.dissemination`.*

Once a record is written, how does it reach the other trusted nodes?

The connect-time sync round already moves what a peer is missing; the question is whether anything announces a change between rounds. An overlay makes a change visible sooner and adds a 0.x dependency outside iroh's wire promise, so it waits on the scope model that says who may hear the announcement at all.

**The alternatives it offers.**

- `gossip_overlay`: Announce changes on an iroh-gossip topic per share, keeping the sync round as the repair path and the only thing that moves canonical bytes. Gossip is 0.x and outside the 1.0 wire promise, so it must be pinned and kept behind the carrier port.
  - taking it would make `metadata_exposure`, `traffic_budget_numbers` live.
- `sync_round_only`: Keep only what exists: one pull each way plus a best-effort push to the home node. Nothing new is taken on, and a change is noticed at the next round rather than when it happens. **(the recorded lean, starred in the box)**

**Must be decided first**: `discovery_fold` (Decided), `scope_model` (Lean), `transport_key_binding` (Lean), `version_pin` (Lean).

**Deciding it is what `registry_growth` is waiting for.**

**Sources**: `IrohGladeMapping §4.2`, `INV-D5`, `INV-D6`.

### identity_adapters

*tier `third`, matrix row Q7, status **Lean**, declared as `IdentityAdapters` in `glade_decisions:GladeDecisions.identity_adapters`.*

Does v1 talk to an existing company directory, or only to grants made by hand?

The trust-provider interface exists either way, and it answers only "is this assertion real?"; deciding what a principal may do stays with the capability model. The question is whether any adapter ships in v1, because each one is a foreign identity source to keep working. It waits on what a capability proof looks like.

**The alternatives it offers.**

- `kerberos_ldap`: Read facts from Kerberos, Active Directory or LDAP through an adapter. It reaches the older corporate estate, and it is another adapter kept current with someone else's schema.
- `none_in_v1`: Ship with device certificates and grants made by hand, keeping the trust-provider interface declared and unimplemented. Nothing foreign has to be kept working, and anyone with an existing directory wires it up themselves. **(the recorded lean, starred in the box)**
- `oidc`: Accept an OIDC or OAuth2 token as an authentication input at the edge. It is the proof kind most organisations already issue, and it makes an outside issuer part of who gets in.
- `spiffe`: Take workload identities from SPIFFE or SPIRE for nodes and providers. It fits a fleet that already issues them, and it assumes that fleet exists.

**Must be decided first**: `proof_family` (Lean).

**No other question is waiting on it.**

**Sources**: `AZ-3`, `SEC-55 trust providers`.

### relay_posture

*tier `third`, matrix row Q1, status **Lean**, declared as `RelayPosture` in `glade_decisions:GladeDecisions.relay_posture`.*

Whose relays and whose DNS does the first real route run on?

A real route needs somewhere to fall back to when a direct connection cannot be made, and somewhere to look addresses up. n0's free tier says in its own terms that it is not suitable for production and that a relay operator sees connection metadata, while the discovery model still assumes a public iroh relay; that wording has to move too.

**The alternatives it offers.**

- `community_dev_only`: Use n0's free public relays for development only. They cost nothing, are rate limited and carry no uptime guarantee, and n0 advise against them for sensitive data.
- `iroh_services_pro`: Pay 19 USD a month for authenticated shared relays with a rate limit, an egress allowance and support tickets. Nothing has to be run, and connection metadata sits with someone else.
- `self_hosted`: Run n0's own iroh-relay and iroh-dns-server yourself; the binaries are the ones they run, and it is free beyond the hosting. Authenticated relays come with it, through an allowlist or a shared password, so a leaked relay address alone is useless. **(the recorded lean, starred in the box)**

**Must be decided first**: `transport_key_binding` (Lean), `version_pin` (Lean).

**No other question is waiting on it.**

**Sources**: `IrohReview §7`, `GladeDiscoveryModel §5`.

### bulk_transfer

*tier `gated`, matrix row Q5, status **Lean**, declared as `BulkTransfer` in `glade_decisions:GladeDecisions.bulk_transfer`.*

How does something too big for a record get moved, and is that worth building yet?

Verified, resumable, content-addressed transfer is genuinely missing from Glade and would be wanted by file suppliers, snapshot bootstrap and large exchange results. Whatever carries it must sit behind the same admission and budget rules as the ordinary carrier, not become a second delivery path around them.

**The alternatives it offers.**

- `defer_bulk`: Build no bulk path at all until a supplier actually declares one. It costs nothing now, and the first supplier that needs one waits for it.
- `iroh_blobs_port`: Adopt iroh-blobs behind a new bulk-transfer port. Authorisation is only the provider's event handler, so Glade must map each requested hash to its owning share and check per request; the crate's own docs still say it is not production quality. **(the recorded lean, starred in the box)**
- `own_chunked_streams`: Frame our own chunks over QUIC streams. Nothing 0.x is taken on, and there is no content addressing, so verification and resumption would have to be built.

**Must be decided first**: `version_pin` (Lean).

**No other question is waiting on it.**

**It is gated by**:

- `first_bulk_supplier`: A supplier declares a bulk profile: files, snapshots or large results.

**Sources**: `IrohGladeMapping §4.3`.

### registry_growth

*tier `gated`, matrix row Q12, status **Lean**, declared as `RegistryGrowth` in `glade_decisions:GladeDecisions.registry_growth`.*

When the registry outgrows one shard, what splits it, and does anything need ordering?

The growth target is a design target of roughly a million machines, not a demonstrated result, and it means sharded registries, referrals between them and bounded indexes over them. The real question is which parts, if any, ever need ordered coordination, because that is the one thing the fold cannot do.

**The alternatives it offers.**

- `delegated_referrals`: Let a shard hand a caller on with an authenticated referral, with local preference, over the same fold. The layout can change without a central edit, and no device has to hold every entry; there is still no ordering guarantee across shards.
- `ordered_reconfiguration`: Back shard splits, moves and membership with consensus. It is the only option that makes reconfiguration ordered, and the only one that brings a consensus library into a system that deliberately kept one off the read path.
- `trusted_mapping_only`: Write down which namespace lives on which shard and trust that mapping. Nothing is dynamic and nothing has to agree, and every change to the layout is made by hand. **(the recorded lean, starred in the box)**

**Must be decided first**: `dissemination` (Lean).

**No other question is waiting on it.**

**It is gated by**:

- `failure_model`: A written registry failure and membership model exists.
- `first_real_route_slice`: The fixed-peer iroh route slice from GladeBuildEntry passes.

**Sources**: `GAD-04`, `GAD-05`.

### simulator_tooling

*tier `gated`, matrix row Q13, status **Lean**, declared as `SimulatorTooling` in `glade_decisions:GladeDecisions.simulator_tooling`.*

Do we bring in outside simulators and dependency-policy tools, or stay on our own?

The kernel oracle, glade-discover-sim and the taut corpora are already ours and decided, and the outside tools were never evaluated and would be complementary at most. The matrix says not to look before the first real route passes, so what is really being weighed is the cost of looking early.

**The alternatives it offers.**

- `dependency_policy_tools`: Run cargo-deny and its relatives beside the own architecture gate. They cover policy the local gate does not, and the matrix judges them complementary at most.

### store_engine

*tier `gated`, matrix row Q8, status **Lean**, declared as `StoreEngine` in `glade_decisions:GladeDecisions.store_engine`.*

When does the whole-state blob stop being good enough, and what takes over?

The seam is already fixed: StoreApi holds a blob now, a real engine may sit behind it later, and an engine is never the replication mechanism. What is open is the measured point at which the blob hurts, and which engine is worth an evaluation then.

**The alternatives it offers.**

- `redb_engine`: Put redb behind the same seam instead: pure Rust, and already used by iroh's own crates. It has not been evaluated for Glade, and n0 note friction running an embedded database inside async, so taking it means doing that evaluation first.
- `sqlite_engine`: Put SQLite behind StoreApi when the blob stops paying. It is the successor the seam ruling already names, and it stays a store engine: replication stays in the ops.
- `whole_state_blob`: Keep writing the whole state as one taut blob. Nothing changes and nothing is added, until size or query volume makes rewriting it hurt. **(the recorded lean, starred in the box)**

### text_engine

*tier `gated`, matrix row Q9, status **Lean**, declared as `TextEngine` in `glade_decisions:GladeDecisions.text_engine`.*

Does collaborative text stay on our own engine, or does a second one come in beside it?

text_crdt is already a profile over the own crdt engine and it ships. A second engine could only enter as another profile with conformance rows of its own, and it brings its own wire format and its own browser bundle with it.

**The alternatives it offers.**

- `automerge`: Admit Automerge 3.x, a Rust core reached from JavaScript through Wasm. Its browser bundle is by far the largest of the three, which every browser fold would carry.
- `loro`: Admit Loro 1.x, which orders text with Fugue and benchmarks well on large replays. There is no Python parity, so the three-language corpus could not be kept whole.
- `own_text_profile`: Keep text_crdt.profile/v1 over the own crdt engine, which is already shipped. No new engine and no new wire format, and whatever it cannot do stays undone. **(the recorded lean, starred in the box)**
- `yrs`: Admit the yrs/Yjs family as a second profile engine. Its binary compatibility with Yjs is documented and its browser bundle is the smallest of the three; the Python leg through pycrdt is stated as intent rather than guaranteed.

**Must be decided first**: `shape_catalogue` (Decided).

### metadata_exposure

*tier `branch-induced`, matrix row R8, status **Open**, declared as `MetadataExposure` in `glade_decisions:GladeDecisions.metadata_exposure`.*

What can a node or relay learn about a share it holds no grant for?

The table the sources asked for now exists (GladeMetadataExposureTable). Transport encryption hides everything from a relay but endpoint ids, timing and volume, while an accepted node is handed the whole directory, and as of 2026-09-21 nothing in the node checks a grant before serving a share. The four answers are a ladder: each one includes the one before it.

**The alternatives it offers.**

- `granted_shares_only`: Filter what a peer or session is offered by the grants its operator or principal holds, at the one point the sync path already names, so nothing of a share reaches a node with no grant for it. It makes this question's own premise true for one fold query on the serve path. The directory still replicates whole, so share ids, principal names and the grant table stay visible to every accepted node, and a stale fold needs a defined fail direction.
- `legible_by_design`: Accept that any node the operator accepts sees the whole directory in plaintext: every workspace id, share id, principal name and grant, plus the heads of any share it asks for. Nothing is built and debugging stays readable. The security analysis's advice to treat readable names as sensitive is refused rather than deferred, and a node later found to be someone else's has already read the list.
- `opaque_wire_ids`: Replace share, glade and origin ids on the wire with opaque derived ids, keeping the readable names in a mapping only granted peers hold. It is the only option that closes the name leak against a relay and a lookup service as well as a peer, and the only one that matches the table the security analysis drafted. It costs a wire change, the readability of every log, trace and test, and a mapping kept correct forever.
- `policy_zone_split`: Keep the directory replicating everywhere, but move the policy streams into a zone only nodes holding a policy grant receive, using the per-zone chains that already make a zone filterable. An ungranted node then learns that shares exist but not who may touch them. It costs a second replication rule, a boot path for a node that has the shares but not the policy, and the property that the directory is one ordinary share.

**Must be decided first**: nothing.

**No other question is waiting on it.**

**It is only live if** `gossip_overlay` or `node_trust` is taken.

**Sources**: `GDL-010`, `WD-3`, `GladeMetadataExposureTable §7`.
