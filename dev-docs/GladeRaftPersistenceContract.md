# Glade Raft Q2 persistence and recovery contract

Date: 2026-10-03. Status: **proposed experimental boundary; implementation awaits contract review**.

This document refines Q2 in [GladeRaftQualificationPlan.md](GladeRaftQualificationPlan.md), principally RA-003/004/005/006/010/011 in [GladeRaftAdoptionContract.md](GladeRaftAdoptionContract.md). Q1a's accepted memory proof does not qualify persistence. This is a controlled local-disk/process-crash profile, not production adoption of raft-rs or a ratified production durability promise. Q2 MUST include the actual RawNode persistence/replay path and a process-kill witness; closing only the file adapter is insufficient.

## 1. Scope, ownership and dependency boundary

The experiment remains the independent `proofs/raft-adoption` workspace. `glade-raft-durability-api` is a dependency-free contract crate with meaningful dyn-compatible `DurableStore::load` and `persist` operations. `glade-raft-disk` is its replaceable std-only implementation. The proof harness depends normally on the contract and chooses the disk adapter only in development composition/tests. No production Glade/Gyld dependency or canonical wire format changes.

These role/edge/inventory changes are **proposals for the Q2 contract review**, not silent allowance relaxations. The contract inventory/source scans include the new crates; there are no process-global exception entries. File paths, expected bindings, trusted recovery floor and fault hooks MUST be caller-supplied instance inputs. The eventual host remains responsible for Raft and application semantic validation. Storage owns physical local publication and single-writer access. Records/application replay owns ordered payload and retained outcomes. Existing Admission/Policy responsibilities are unchanged; this does not authorize unsigned production policy.

## 2. Named profile and explicit limits

The profile uses scope 7, logical voter ID 1/2/3, canonical fixed voters `[1,2]` or `[1,2,3]`, and application profile 1. Every configured voter stores the complete protected command bytes, not ownership metadata alone. There are no snapshots, prefix compaction, membership changes, network transport, external effects or production crypto in Q2. Three local voter files are not three independent physical failure domains.

The first actual I/O/process-crash witness runs on local APFS/macOS. Successful store writes MUST call `File::sync_all`; explicit genesis additionally MUST synchronize the owning parent directory after creating the file. The evidence MUST record host/toolchain/filesystem and actual operations. It does **not** certify power-loss survival, drive/controller cache behavior, arbitrary filesystem guarantees or physical quorum independence. A process kill leaves the kernel/filesystem running. Simulated short writes and corruption are adversarial protocol tests, not physical power-cut tests.

Checksums protect accidental corruption only. The journal and its directory are trusted owned storage: malicious writers, path replacement, symlink substitution, tampering that recomputes checksums, and rollback of every copy plus its external floor are outside this profile. OS file locks protect cooperating opens of the same file inode; they do not confer distributed resource ownership or fence rogue path replacement.

## 3. Boundary values and lifecycle

`Binding { scope, node, voters, application_profile }` binds a store to one exact fixed logical instance. `StoredEntry { index, term, bytes }` carries normalized framing and original complete protobuf Entry bytes. `DurableImage { term, vote, commit, entries }` carries hard state and the entire uncompacted log from index 1. `StoredState { revision, binding, image }` is one coherent image. The contract exposes no raft-rs, protobuf, transport or runtime type.

`DiskStore::create_new(path, binding)` is the sole explicit genesis operation; it MUST use exclusive creation and MUST NOT reset an existing file, including an empty/corrupt file. `open(path, expected_binding, minimum_revision)` MUST NOT create or initialize missing storage. Invalid requested bindings MUST fail before creation. Genesis is revision 0, empty entries, term/vote/commit 0. A known missing/empty file is not evidence that an existing scope can safely restart from genesis.

`load(&mut self)` returns the latest accepted coherent state. `persist(&mut self, expected_revision, image)` compares the exact current local revision and, on success, returns the next revision and exactly the supplied image with unchanged binding. A stale expected revision produces `RevisionConflict { expected, actual }` without mutation. Revisions MUST increase by one using checked arithmetic. This operation is local serialization, not a distributed compare-and-swap or authority claim.

## 5. Journal format and publication model

The proposed adapter uses an append-only journal of checksummed **full images**, including a revision-0 genesis record. Each record MUST contain a format-version/magic boundary, bounded length, exact binding, revision and all image fields/Entry bytes, protected by an accidental-corruption checksum (CRC). Recovery MUST consume the entire file with no accepted trailing bytes. Revision sequencing plus immutable prior committed prefix checks detect record gaps/interior loss and conflicting transitions; the journal is not a cryptographic authenticity chain. A valid old prefix substituted as the whole file remains indistinguishable without RP-007's separate floor.

A record success requires complete `write_all` followed by `sync_all`. The adapter MUST hold one exclusive OS file lock for the store lifetime, including recovery validation. Newly created genesis additionally synchronizes its existing parent directory. No automatic directory creation, truncation, stale-lock breaking, journal repair or disaster reset is part of this contract. If genesis creation fails after creating the file, the file MUST remain evidence for explicit reopen/quarantine rather than be automatically removed and replaced.

At load, the latest complete image is accepted only if **all** records validate. At persist, validation/revision checks happen before publication; illegal transitions and capacity rejections MUST leave the instance usable. Once a write begins, the caller cannot know from an error alone whether a complete record survived. The driver MUST refuse further serving until recovery. Reopen can recover the previous/full new coherent result or quarantine a partial record. The fault fixture deliberately writes a partial record to prove fail-closed recovery.

Retained application state is reconstructed deterministically from complete committed log bytes and application profile 1, including the private readiness evidence. There is no independently acknowledged application checkpoint with a separable cursor. This avoids acknowledging an outcome whose supporting complete history is absent; full replay has unbounded startup/storage costs and does not replace Q3 snapshot qualification. Replay uses the same trusted private committed path as the live driver; public exact-index replay continues to recover the retained canonical receipt under the Q1a contract.

## 6. Fault and receipt matrix

| Cut/fault | Live result | Reopen requirement |
|---|---|---|
| Invalid image/revision/capacity before publication | Explicit rejection; no mutation | Prior coherent state |
| Injected before-write I/O failure | I/O error; unchanged instance MAY continue; driver stops serving | Prior state, unless an explicit retry subsequently succeeds |
| Partial write | I/O error; poisoned; no messages/apply/receipt from failed Ready | Quarantine torn journal |
| Complete append, before/during sync | I/O error or killed process; unknown publication; poisoned if alive | Full coherent result or quarantine/prior coherent prefix as justified by actual persisted evidence; no failure-as-noncommit inference |
| After sync, before driver apply | Persisted command may be committed; no premature receipt | Replay committed prefix; preserve uncommitted entries without apply |
| After apply, before client receipt | Lost reply; one retained outcome | Exact retry returns original receipt subject to current disclosure rule |
| After receipt | Receipt promises named local process-crash profile and data-bearing quorum application evidence | Actual kill/restart recovers original receipt/payload/fences |
| Old complete journal replacement | Out of detection range without external floor | With trusted floor reject; without floor admit only explicitly qualified older observation |

The one-shot `FaultPoint` inputs are `BeforeWrite`, `PartialWrite`, `AfterWrite`, `BeforeSync`, and `AfterSync`. They reside on each store instance and are test controls, never process-global hooks. `AfterWrite` and `BeforeSync` may coincide physically; both names make consumer boundary intent explicit. Live driver apply/reply cuts require separate host/process witnesses.

## 7. Delivery and review gates

1. Pin this contract, separate crate roles/edges, compilable dyn consumer and reusable semantic tests. Disk scaffold MUST return `NotQualified`; execute and retain RED evidence before disk implementation. Host recovery constructor/scaffold tests MUST likewise fail behaviorally before integration.
2. Obtain independent Consistency/Safety review of the **same committed source tuple**. Resolve P0/P1/P2 findings before changing implementation. Public boundary changes require fresh review as specified by the review loop.
3. Implement the adapter and injected host in small TDD steps. Run shared semantic conformance against both the model and real disk, actual I/O/fault/restart tests, existing Q1a regression tests, architecture/source/process-global/fmt/clippy checks. Run the process-kill witness externally with explicit paths/environment and no production Rust child-spawn/global-state exception.
4. Obtain independent Code/State review of the same completed source tuple and settle findings. File reports verbatim in the qualification ledger. Evidence MUST identify accepted source and partial/open claims.

The small API/model loop is `cargo test --locked --offline --manifest-path proofs/raft-adoption/Cargo.toml -p glade-raft-durability-api`. The concrete I/O loop is the same command with `-p glade-raft-disk`. The driver target is `-p glade-raft-adoption-proof --test recovery`; the separate process witness is `python3 proofs/raft-adoption/process-crash.py --worker <compiled integration-test executable>`. The ignored Rust test worker reads its injected argument environment only in test code. Python launches it with an explicit minimal environment and kills it using SIGKILL at two cuts: after an index-3 payload-23 receipt, and after persisting commit index 3 before application/reply. Both MUST reopen and replay the committed payload and original receipt. This tool does not add a production Rust child-spawn exception. These tiers MUST stay separate from pure memory edit loops. Durations remain unmeasured at this contract checkpoint; no latency guarantee is claimed.

Q3 snapshots/membership and Q4 production library/environment/randomness/bootstrap/legacy writer exclusion remain open. Q2 cannot select physical production failure domains or promise production power-loss durability by implication.

Primary Rust API references: [File::try_lock](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock) (available since Rust 1.89; OS-handle lifetime and advisory/platform limits) and [File::sync_all](https://doc.rust-lang.org/std/fs/struct.File.html#method.sync_all). These API contracts do not certify this experiment's power-loss behavior.
